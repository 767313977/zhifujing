# S6 性能风险登记

| 指标 | 实测 | 预算/目标 | 结论 |
| --- | --- | --- | --- |
| 10 板块工作台 SQL | **53** | ≤25 | **未达标**（`PERF_SQL_BUDGET_NOT_MET` 保留） |
| 10 板块 P50 | 135.94–165.28 ms | 无已批准 SLO | 未观察到超时 |
| SQL 自身耗时 | 38.8 ms | — | 其余为 ORM/Python 组装 |
| 重复查询合计 | ≈4 ms | — | 合并也无法把 53 降到 25 |
| quality overview（30 天） | 21 SQL / 47–52 ms | — | 可接受 |
| sentiment next day（250 天） | 255 SQL / 0.46–1.88 s | — | 慢，但非灰度首屏 |
| peak 内存 | ≤13.5 MB | — | 未见异常 |

## 风险

1. 53 SQL 的固定成本来自多组独立查询；灰度只读流量下延迟可接受，但没有
   已批准的 SLO 作为扩量依据；
2. `sentiment_next_day` 250 天查询在冷缓存下接近 2 s，可能触发网关超时；
3. 未做 soak / 数据库锁争用测试。

## 建议

- 灰度期间监控 API P95 与 SQLite busy；
- 先在内部 allowlist 观察，不按比例扩量；
- 后续按 `benchmark-before-after.md` §5 做批量查询改造，并以字段级黄金样本验证。

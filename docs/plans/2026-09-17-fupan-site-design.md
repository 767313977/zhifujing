### 1.5 iFinD 的坑（设计必须处理）

1. **`symbols` 单次上限 10 只，超出静默丢弃且不报错**
   实测传 11 只 → 只返回 10 只，第 11 只（中信证券）无声消失。必须自行分片。
2. **自然语言工具返回 Markdown 表格字符串，不是结构化数组**
   `search_stocks` / `get_stock_performance` / `sector_data` 都在 `data.answer` 里塞一张
   或**多张** Markdown 表。需要写 Markdown 表格解析器。
3. **返回结果混入非交易日**
   实测要 20 个交易日 → 返回 29 行，含周末；非交易日的涨跌幅/成交额为空 `\t`，
   收盘价为前一交易日填充值。必须按交易日历过滤。
4. **表头单位与数值单位不一致**
   表头写 `成交额（单位：元）`，值是 `22.1734亿`。解析需按"亿/万"自行换算。
5. **板块代码体系混用**
   `sector_data` 对"半导体"返回**中信行业分类**（`001033206010`），
   对"证券"返回**同花顺行业类**（`00103512701`）。口径不统一，必须在 query 中显式指定分类体系。
6. **全市场涨跌停家数不完整**
   `index_highfreq_quotes` 的涨跌停家数只对**上证指数**和**深证成指**有值；
   **深证综指、中证全指返回 `null`**。而深证成指仅含 500 只成分股，
   导致深市涨停家数被严重低估。**全市场涨停口径只能靠 akshare 涨停池**。
7. **限流严格且报错方式隐蔽**（P1 实测补充）
   - 权益：免费版 2 请求/秒、个人版 5、企业版 10
   - **突发会触发 429**：一次性放行 4 个请求即返回
     `{"answer":"用户请求过于频繁，请稍后重试"}`
   - **429 时 HTTP 状态码仍是 200**，错误藏在工具结果文本里。若只在
     HTTP 层判错，429 会被误当成 JSON 解析失败而**不重试**
   - 对策：令牌桶**不预留突发额度**（capacity=1，请求按 1/rate 秒均匀放出），
     并在重试范围内按文本识别限流

### 1.6 iFinD 的能力缺口（由 akshare 补齐）

grep iFinD 全部 9 个参考文档，`涨停|跌停|龙虎榜|资金流|连板|封板` **仅命中 1 行**
（指数级"涨停家数/跌停家数"）。以下**iFinD 完全没有**，而它们是 A 股复盘的核心：

| 缺口 | akshare 接口 | 实测 |
|---|---|---|
| 涨停池（含连板数、封板资金） | `stock_zt_pool_em` | ✅ 89 条 |
| 跌停池 | `stock_zt_pool_dtgc_em` | ✅ 4 条 |
| 炸板池 | `stock_zt_pool_zbgc_em` | ✅ 11 条 |
| 龙虎榜 | `stock_lhb_detail_em` | ✅ 73 条 |
| 交易日历 | `tool_trade_date_hist_sina` | ✅ 8797 条 |
| **全市场涨跌家数** | `stock_market_activity_legu` | ✅ 见下 |

**全市场涨跌家数（乐咕乐股）**：iFinD 的涨跌家数只对上证指数有效
（深证A指/国证A指/中证全指均返回 `null`），而深证成指仅含 500 只成分股。
改用 `stock_market_activity_legu`，**一次调用**给出全市场宽度，且该接口走乐咕乐股、
与东财集群无关，不受频控影响：

```
上涨 2503 / 下跌 2558 / 平盘 148 / 停牌 12 / 活跃度 47.94%
涨停 50（真实涨停 47 + ST涨停 3）/ 跌停 2
```

**交叉验证通过**：乐咕的「真实涨停 47」与 akshare 涨停池的 47 条完全吻合，
两个独立数据源互证。

### 1.7 akshare 侧的已知问题

`push2*.eastmoney.com` 集群（全 A 快照、板块列表、个股资金流、个股日线）会因请求频率
触发**本机 IP 临时频控**（实测连接级失败，等待 75s 未恢复）。
`push2ex.eastmoney.com`（涨停池/龙虎榜）是独立集群，不受影响。

因此：**只用 akshare 的 `push2ex` 系列接口**（涨停池/跌停池/炸板池/龙虎榜），
不碰 `push2` 系列。全 A 快照类需求由 iFinD 承担。

## 4. 采集流程

**触发时机：** 交易日 15:05 后（收盘数据已稳定）+ 支持手动补数。

顺序（每步独立事务、独立日志、失败不阻塞后续）：

1. 交易日历（akshare）
2. 指数日线 + 涨跌家数（iFinD `index_highfreq_quotes` / `index_data`）
3. 涨停池 / 跌停池 / 炸板池（akshare `push2ex`）
4. 板块行情 + 成分股（iFinD `sector_data`）
5. 龙虎榜（akshare `push2ex`）
6. 自选股 + 最近选股结果的个股快照（iFinD `stock_highfreq_quotes`，按 10 只分片）
7. 计算并写入 `market_sentiment`

> **不再做全市场日线落库。** 原先 akshare 方案要拉 ~5400 只股票（触发频控），
> 而现在"找票"由 iFinD `search_stocks` 直接承担，无需本地全市场库。
> 本地只存**自选股 + 选股结果**的个股日线，数据量下降两个数量级。

**限速策略：**

- iFinD：个人版 4 req/s（上限 5，留余量），**令牌桶不预留突发额度**
- akshare（push2ex）：1 req/s
- 失败退避：2s → 4s → 8s，最多 3 次
- **`stock_highfreq_quotes` 必须按 10 只分片**（超出会静默丢弃）

### 4.1 历史回补能力边界（P1/P2 实测修正）

部分数据源**只提供当日值**，对历史日期取数会把今天的数据写到过去。
这类静默的数据污染比直接失败更危险，因此在代码里**硬性拦截**（`_require_today`）。

| 数据 | 可否回补 | 途径 / 原因 |
|---|---|---|
| **指数日线**（收盘价、涨跌幅、成交额） | ✅ 115 天 | iFinD `index_data` 自然语言接口支持历史区间 |
| **涨停 / 跌停 / 炸板池** | ⚠️ 仅最近 **15 个交易日** | 数据源只保留 15 个交易日，更早的日期记 `None` |
| **龙虎榜** | ✅ 128 天 | akshare 接口支持区间查询，一次可取一个月 |
| 情绪指标：涨停数、跌停数、炸板数、封板率、炸板率、最高连板 | ⚠️ 同三池窗口 | 由三池推导 |
| 情绪指标：两市成交额 | ✅ 115 天 | 由回补后的指数表推导 |
| **指数涨跌家数** | ❌ | 同一指数同一天，`index_data` 与 `index_highfreq_quotes` 给出不同数值（实测上证 0917：991 vs 1062），混用会破坏序列一致性 |
| 全市场涨跌家数 | ❌ | 乐咕乐股仅返回当日 |
| 打板效应（昨日涨停股今日均涨幅） | ❌ | 依赖当日实时涨幅 |

**结论**：指数与龙虎榜可补满 6 个月；情绪曲线受三池窗口限制只能覆盖最近 15 个交易日。
不可回补的项在历史记录里留 **`None`**，绝不留 0。

#### 回补时踩到的四个坑

**1. `N日成交额` 是滚动累计，不是单日成交额。**
iFinD 在指标名不明确时会自动生成 `N日成交额（单位：元）`，实测约为单日值的 5 倍。
必须显式写「成交额」才会返回单日 `成交金额`。代码里对列名做了显式排除（`_single_day_amount`）。

验证：0917 上证 `index_data` 单日成交金额 = 8687.7307亿，
与 `index_highfreq_quotes` 的 868,773,070,000 **完全一致**。

**2. 同一指数会返回两套交易所代码。**
中证1000 既有 `000852.SH` 也有 `399852.SZ`（实测重叠日期收盘价与涨跌幅完全一致：
7691.3691 / -1.0174），而且**同一次回补的不同日期区间会返回不同的那个** ——
按 120 天分块时，前一块返回沪深某一边，后一块返回另一边，结果同一指数被存成两套代码。
对策：`INDEX_CODE_ALIASES` 做代码归一。

**3. 回补不能覆盖当日数据。**
`index_data` 写入的行带 `up_count=None`，若用 merge 覆盖当日行，会把
`index_highfreq_quotes` 取到的涨跌家数抹掉。对策：回补只填空缺，跳过已有 (date, code)。

**4. 「取数失败」与「当天真的 0 家」必须在数据层就分开。**（最隐蔽的一个）

三池的数据源只保留最近 **15 个交易日**，超出后行为各不相同：

| 接口 | 超期行为 |
|---|---|
| 跌停池 / 炸板池 | akshare 自查 30 自然日，超出**抛错** |
| **涨停池** | **不做任何校验，只是返回空表** |

第一版实现里，空表和「当天没有涨停」在代码里完全无法区分，结果
**113 天的 `limit_up_count` 被记成了 0** —— 情绪曲线上那些天会显示成「零涨停」，
与事实相反，而且从数据上看毫无异常。

对策分三层：
1. 按**交易日**判断窗口（`POOL_HISTORY_TRADING_DAYS = 15`），超期记 `skipped` 而非 `ok`
2. `limit_up_count` 等指标为 `None` 表示无数据，与真实的 0 严格区分
3. 每个池单独记一条 `pool_*` 日志，情绪计算**只认每个池最新一条**——
   同一日期可能被采集多次，旧日志里残留的 `ok` 会让已超期的池被误判为有数据

修正后：窗口外 113 天为 `None`，窗口内 15 天有真实值，
其中 09-01 与 09-08 的「跌停 0 家」被正确保留为 0。

### 8.3 P3 情绪周期页

**核心设计取舍：长周期看指数，短周期看情绪，两者分开成图。**

三池数据源只保留 15 个交易日，而指数有 115 天。若把它们画在同一时间轴上，
要么指数被截断成 15 天（浪费掉 6 个月背景），要么把 15 天的情绪数据拉伸到 115 天
（视觉上撒谎）。所以拆成三个图并**各自标注实际区间**：

| 图 | 区间 | 内容 |
|---|---|---|
| 指数走势 | 115 个交易日 | 5 条指数线（首日归一为 100）+ 灰色两市成交额柱 |
| 情绪指标 | 15 个交易日 | 涨停/跌停/炸板柱 + 封板率折线（右轴） |
| 连板高度 | 15 个交易日 | 最高连板柱 |

两图之间放一条琥珀色提示条显式说明「两者是并列关系，不是同一时间轴」，
页面底部另有「口径说明」交代每个指标的定义与哪些无法回补。

**新增接口**：`GET /api/market/index-history?days=` 返回按日期升序对齐的
`{dates, series[{code,name,close[],pct_chg[],amount[]}]}`，各数组与 `dates`
严格等长、缺失为 null，可直接喂给图表。

**实现要点**：

- 首日归一为 100，否则点位数量级不同的指数（上证 3875 vs 创业板 3298）无法同轴比较
- 指数配色刻意**避开红绿**，因为那两个颜色在本站有涨跌含义，改用金/蓝/紫/青/粉
- ECharts 走 `echarts/core` 按需注册。直接 `import 'echarts'` 会让产物从
  278KB 涨到 1.4MB；按需后为 821KB（gzip 271KB）

**浏览器实测修掉的 3 个缺陷**：

1. 指数图的图例漏了「两市成交额」——柱序列必须显式写进 `legend.data`，不会自动出现
2. 「口径说明」里的 `**无法回补**` 把星号当字面量渲染了（JSX 不解析 markdown）
3. 图例画在绘图区内部、被高柱压住 → 给 `grid.top` 留 46px 并把图例固定到顶部，
   实测图例与绘图内容之间有约 29 CSS px 的纯空白分界

三图渲染、区间标注、tooltip（成交额已换算为「万亿」）、无横向溢出均已验证。

### 8.4 P3 涨停复盘页

页面定位是**分析**而非再列一遍明细（明细在今日复盘已有），所以要避开重复。
核心新增是**连板晋级率**。

**新接口**：`GET /api/limit/promotion?days=15`

```
连板晋级率 = 昨日 N 板股中、今日晋级到 (N+1) 板的比例
整体晋级率 = 昨日涨停股中、今日仍涨停的比例
```

它衡量的是「昨天的高度能不能被今天接住」：晋级率同步走高说明资金愿意接力，
快速回落说明高位股开始被抛弃。返回对齐数组（`dates` + 各档的
`counts/promoted/rates`），直接喂图表。

**两个刻意的口径处理**：

1. **窗口内最早那天只当基数、不出现在结果里**。算某天晋级率需要它前一日作基数，
   而池子只有 15 天，所以只能得出 14 天晋级率。若不这样做，最早那天会因为
   「前一日无数据」而算出一堆假的 0%。
2. **昨日该档无票时返回 `null` 而非 0**。0 会被读成「该档全军覆没」，
   与「该档当天没有股票」是完全不同的结论。

**页面组成**：

| 区块 | 内容 |
|---|---|
| 连板晋级率 | 4 格统计（最新整体晋级率 / 基数 / 晋级数 / 口径）+ 折线图（1进2 / 2进3 / 3进4 / 整体） |
| 涨停梯队 | 复用，但支持日期切换，可回看任意一天 |
| 首封时间分布 | 首封时间分 7 桶柱状图。首封越早说明资金越坚决 |
| 涨停行业分布 | 横向条形列表（不用图表：行业名较长，轴上放不下） |
| 涨停 / 炸板明细 | 复用明细表 |

**只展示 1进2 / 2进3 / 3进4 / 整体四条线**：4进5 及以上每日基数常只有 1-3 只，
晋级率会在 0% 与 100% 之间反复跳，画出来只是噪声。

**验证**：晋级率做了 5 项手工交叉核对，与接口结果完全吻合。

```
前一日 2026-09-16 有 89 只涨停，当日 2026-09-17 有 47 只
1进2: 基数77 晋级5  手工 6.5%  接口 6.5%   ✓
2进3: 基数9  晋级3  手工 33.3% 接口 33.3%  ✓
3进4: 基数1  晋级0  手工 0.0%  接口 0.0%   ✓
4进5: 基数1  晋级1  手工 100.0% 接口 100.0% ✓（澳弘电子 4板→5板）
整体: 基数89 晋级9  手工 10.1% 接口 10.1%  ✓
```

数据也与盘面自洽：09-16 整体晋级率 37.5%（情绪高潮），09-17 降到 10.1%，
对应涨停数从 89 掉到 47 的退潮。

**浏览器实测修掉的 2 个缺陷**：

1. 行业分布容器 `max-h-[240px]` 装不下 12 行（实际需要 284px），第 12 行被裁一半
   → 提到 320px，实测 `clientHeight = scrollHeight = 284`，无滚动条
2. tooltip 的 `valueFormatter` 只判了 `null`，但 ECharts 对空值点传的是 `'-'`，
   会渲染成 `-%` → 两种都归成占位符

### 8.5 P4 选股器

**为什么只有自然语言一条路径**：本站**不做「本地全市场结构化筛选」** ——
全市场日线不落库（那会触发东财频控，见 1.7），所以本地没有可供 SQL 筛选的全市场表。
找票只能走 iFinD 的 `search_stocks`。这恰好也是当初选 iFinD 方案的主要理由：
一句自然语言就能表达多指标组合条件，覆盖的维度远多于自建筛选器。

**iFinD 返回里的两个元信息字段，名字都极具误导性**（均实测确认）：

| 字段 | 看起来是 | 实际是 |
|---|---|---|
| `selectedSecuritiesCount` | 本次返回条数 | **匹配总数**。实测「市值大于100亿的股票」为 1801 |
| `dataTotalVolume` | 匹配总数 | **数据格子数 = 行数 × 列数**。实测 9 行 5 列 = 45、4 行 5 列 = 20 |

**表格上限 100 行，超出会静默截断。** 危险之处在于：iFinD 的提示文案是固定模板
（写着「只返回前1000行结果」，实际只给 100 行），**不能拿文案判断**。
判断是否截断只能用 `matched > returned`。

若按字面理解，UI 会把「市值大于100亿」显示成「找到 100 只」，
把 1801 只的真实匹配藏起来。所以页面在检测到截断时会显示琥珀色警告：

```
结果被截断：实际匹配 1801 只，但数据源每张表格最多只给 100 行。
要拿全建议在条件里加排名限制或收窄范围，例如「…按总市值排名前 50」。
```

**列是动态的**：iFinD 按提问内容决定返回哪些指标，列名还自带日期
（如 `总市值[20260917]`、`涨跌幅:前复权[20260917]`），所以表头不能写死。
前端把方括号里的日期拆出来弱化显示，并按列名语义格式化数值：

| 列名含 | 处理 |
|---|---|
| 涨跌幅 / 涨幅 / 跌幅 / 换手率 / 股息率 | 百分比，涨跌幅带正负号并染色（红涨绿跌） |
| 市值 / 成交额 / 金额 | 换算成 亿 / 万 |
| 涨停 / 跌停 | `1` / `是` 显示为 ✓ |
| 其他 | 数值按需保留两位小数，其余原样 |

**配套的最小自选股接口**（`GET/POST/DELETE /api/watchlist`）：
选股结果要能落下来，否则跑完什么都没留下。代码归一能识别
`600519` / `600519.SH` / `sh600519` 三种写法，重复加入按幂等处理。
完整的自选股页面在 P5。

**浏览器实测修掉的 2 个缺陷**：

1. 列名日期的「弱化」没生效 —— 日期用了 `text-fg-dim`，而表头 `th` 本身就是这个颜色，
   同色同字号等于没效果 → 改为把**列名**提亮到 `text-fg-muted`，形成对比
   （实测列名 `rgb(138,147,160)` vs 日期 `rgb(89,97,109)`）
2. 截断警告的标题不够醒目 → 把「结果被截断：」设为琥珀色 + 中等字重

### 8.6 P6 定时任务与数据管理页

**定时采集**（APScheduler，随 FastAPI 生命周期启停）：

- 交易日 **15:05** 自动采集。时刻是为了等收盘数据稳定。
- Cron 只按 `mon-fri` 触发，**真正的交易日判断在任务内做**（查交易日历），
  这样节假日不会白跑。
- 已采集过就跳过，不重复请求数据源。
- `misfire_grace_time=3600` + `coalesce=True`：机器休眠错过触发点，一小时内仍补跑，
  错过多次也只跑一次。

**针对「本机不常开」的启动补采**：过了采集时刻才启动时，在**后台线程**里检查
当日是否交易日、是否已有数据，缺则补跑。放后台是因为同步跑会阻塞服务启动好几秒。

> ⚠️ 本服务必须**单 worker** 运行。多 worker 会各自拉起一个调度器，
> 同一时刻重复采集。

**采集互斥锁**（顺带修掉的隐患）：定时任务、手动采集、用户连点按钮都可能同时触发。
每个 `DailyCollector` 实例各有自己的令牌桶，两个采集器并发跑等于**实际请求速率翻倍**，
会直接触发 iFinD 429。所以整个采集过程用模块级 `threading.Lock` 串行化，
拿不到锁**直接返回 409 而不是排队等待** —— 排队会让用户以为卡住了。

实测并发发两个采集请求 → `[200, 409]`，不会重复采集。

**数据管理页**（`/settings`）：

| 区块 | 内容 |
|---|---|
| 定时任务 | 运行状态（带脉动指示）、采集时刻、下次/上次运行 |
| 数据覆盖 | 各表分别统计，因为**可回补范围不同**（指数 115 天 / 三池 15 天 / 龙虎榜 128 天） |
| 手动操作 | 立即采集 + 历史回补（可选起始日期） |
| 采集日志 | 最近 30 条，含 `pool_up` / `pool_down` / `pool_broken` 细粒度条目 |

**浏览器实测暴露的一个系统性问题 —— 语义色与行情色混用**：

本站遵循 A 股「红涨绿跌」，所以 `--color-down` 是**绿色**。而代码把 `text-down`
用在了**错误提示**上，导致 **5 个页面的错误横幅全是绿色的**，语义完全读反。

修法是新增语义色令牌，把两种含义分开：

```css
--color-up / --color-down        /* 行情涨跌，只用于价格数据 */
--color-danger / --color-ok      /* 状态语义，用于错误与正常 */
```

两者恰好同色（danger=#ff4d4f、ok=#00b96b）是巧合，但语义分开后未来可以各自调整。

顺带把散在 5 个页面的提示条抽成 `Alert` 组件 —— 之前只有 `/settings` 带 ✕ 关闭按钮，
其余页面没有，这个不一致也是在实测中发现的。

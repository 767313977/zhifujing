## G0. 35 个演练库完成隔离

**要解决的实际问题**：本机 `backend/data/p13_audit/` 下有 6.11 GB 演练库，其中含真实业务数据的副本；它既不是运行必需，也不该留在 TRAE 工作区内被同步、被索引、被误读。

**判定标准**

- 35 个文件（含 `-wal` / `-shm`）全部移到**非同步、非工作区**的受限目录；
- 目标目录与源目录**同一磁盘卷**（跨卷移动是复制+删除，中途失败会留下不完整副本）；
- 移动前后 SHA256 与字节数逐条一致；
- 原目录只剩文本脚本与证据 JSON，无 `.db` 残留。

**关键事实（已核实）**

- Windows 同卷 `Move-Item` 底层走 `MoveFileEx`，**保留源文件 ACL，不重新继承目标目录权限**。因此即使目标目录 ACL 已收紧，被移动的文件仍会带着源目录的 `CodexSandboxUsers:(RX)` 继承 ACE。
- TRAE 工具运行身份 = 当前登录用户 `76731`（管理员组成员）；`codex-windows-sandbox-service` 运行身份 = `CodexSandboxUsers`。两者都可能读取文件内容。
- 由于 `76731` 是管理员，**ACL 只能限制非管理员主体，不能阻止管理员自身读取**（管理员有 `SeBackupPrivilege`，可绕过 ACL 读文件）。要实现真正的内容隔离，必须叠加「加密存储」或「切换到非管理员受限账户操作」。
- **复制 ≠ 隔离完成**：`Copy-Item` 后源文件仍在原目录、仍可被 TRAE 读取。只有在目标副本验证通过 + ACL 重置通过 + 源文件删除之后，隔离才算完成。
- **`/inheritance:e` 不等于清除显式授权**：它只重新启用继承，**不删除**直接分配给该文件的显式 ACE。若源文件有显式 `CodexSandboxUsers` 或 `Authenticated Users` ACE，`/inheritance:e` 后这些 ACE 仍在。必须用 `icacls` 检查并显式 `/remove`。

**判定标准（全部满足才算隔离完成）**

- 35 个文件全部复制到同卷受限目录；
- 目标文件的**显式 ACE 已清除**，仅继承目标目录权限；
- `CodexSandboxUsers`、`Authenticated Users`、`76731`（若非必须）对目标文件均无 ACE；
- 源目录已删除全部 35 个 `.db`/`.db-wal`/`.db-shm`，仅剩文本与 JSON；
- 若无法证明管理员 `76731` 不可读，**必须**采用加密容器（VeraCrypt / BitLocker To Go）作为替代，ACL 仅作辅助。

**收紧后的判定口径（2026-11-10）**

- **原文件仍在可读工作区时，G0 一律不得标记为「已通过」**。复制完成、哈希一致、ACL 收紧都只是中间状态；只有「源文件已删除 且 目标不可被 TRAE 读取」才构成通过。
- **Windows 文件复制、ACL 修改、源文件删除是三个独立动作，需分别书面授权**。本轮不执行其中任何一项（不复制、不改 ACL、不删源）。
- **VeraCrypt / BitLocker 只有在「已卸载 + 密钥不在 TRAE 可访问处 + TRAE 无解密与挂载权限」时才提供有效隔离**。若容器已挂载、且 TRAE 与用户使用同一管理员身份，磁盘上的容器文件仍可被读取 —— 此时它只是「多一个文件」，不等于隔离。
- 因此 G0 的当前状态是**未通过**（源文件仍在原地、容器尚未建立）；不得用「已复制 / 已算哈希」代替。

| 步骤 | 执行主体 | 命令 / 动作 | 影响范围 | 预期输出 |

| 1-6 | `[运维]` | 在目标位置验证 `sha256sum` 与 1-3 一致，`sqlite3 ... "PRAGMA quick_check;"` | 只读 | `ok` + 哈希一致 |

**磁盘空间门槛（按实际挂载点计算，不固定 2GB）**

所需空间 = 生产库大小 × 3（1 份在线备份 + 1 份迁移前备份 + 1 份回滚备用）+ WAL 峰值（同库大小，迁移期间 WAL 可能膨胀到接近库大小）+ 发布包（≈ 50 MB）。

```bash
DB_SIZE=$(stat -c%s /opt/fupan/backend/data/fupan.db)
WAL_PEAK=$DB_SIZE                              # WAL 峰值按库大小估
NEEDED=$(( DB_SIZE * 3 + WAL_PEAK + 52428800 ))
# 分别校验 /opt（库所在）与 /backup（备份所在）的可用空间
df -B1 /opt /backup
# 若同挂载点：可用空间 ≥ NEEDED；若不同挂载点：各自 ≥ 其承担的部分
```

注意：`/opt` 与 `/backup` 若为同一挂载点，按单一剩余空间计算（需 ≥ `NEEDED`）；若分属不同挂载点，`/opt` 需 ≥ 库大小 + WAL 峰值 + 发布包，`/backup` 需 ≥ 库大小 × 2。

**WAL 处置禁令**：**不允许在运行中的生产库上强制执行 `PRAGMA wal_checkpoint(TRUNCATE)`**。该语句会阻塞写入并可能让正在采集的任务报 `database is locked`，也会把 WAL 与主库的提交状态强行改动。WAL 峰值一律按「同库大小」预留空间（见上面的 `WAL_PEAK`），**靠预留空间承受，不靠在线上压 WAL**。若确需压缩 WAL，只能在「服务已停 + 无任何写入者」的离线窗口内做，并计入停服时长。

### RPS 回填行为核实结论（已读源码）

| 项 | 结论 |
| --- | --- |
| 写入方式 | **UPSERT-FILL**：`scan_rps.scan()` → `db.upsert_many_fill()` → `INSERT ... ON CONFLICT(trade_date, code) DO UPDATE SET col = COALESCE(excluded.col, col)`（2026-11-10 由 `upsert_many` 切换） |
| 覆盖风险 | 写入层：`None` **不再覆盖**已有非空值，`0` 仍会正常覆盖。业务层：本次重算判定为「已不可算」的单元格，在**同一事务、同一交易日**内先显式清成 `NULL` 再 upsert，避免过期值冒充当前有效值 |
| 过期语义 | 三类清理：①窗口覆盖 <90% → 只清该档 `ret*/rps*`；②当天有 K 线但全档不可算 → 整行指标清空、保留主键行；③库内有该日行但当天已无 K 线（行情被修订删除）→ 整行清空。范围严格限定 `trade_date == target` |
| 为什么不只靠 COALESCE | COALESCE 只能表达「这次没算这一格」，不能表达「这一格已失效」。行情被修订后旧 RPS 已经错误，若不清空会一直显示旧排名 |
| 状态语义 | `RpsDaily` **没有** freshness/status 列。当前「有行、指标为 NULL」= 缺失 / 待重算，前端按 `coverage.data_status`（`no_rps` / `no_rps60` / `partial_rps` / `no_bars`）告警，不把 NULL 当有效值展示 |
| 触发器影响 | `rps_daily` 有 ai/au/ad 三条触发器，每次 upsert 触发，`rps` 域 revision 递增（逐条）。单日全市场约 5000 行，触发器开销可忽略 |
| 事务边界 | `scan_rps.scan()` 每个交易日一个 `session_scope()`（一个事务），清理与写入同事务、失败一起回滚；回补脚本按日循环，日与日之间独立提交 |
| 清理安全前提 | 破坏性清理前必须同时满足：①当天 K 线达到覆盖率闸；②当天 K 线行数不低于「前 5 个交易日中位数」的 90% 且绝对缺口 < 100 行；③待清理行数 ≤ `max(50, 库内该日行数 × 5%)`。任一不满足 → 整轮 `skipped`（`coverage` / `incomplete_bars` / `stale_guard`），**不写不清**，报「先重新采集当日行情」 |
| 无效写入防护 | 清理 UPDATE 带 `OR(列 IS NOT NULL)`（覆盖全部指标列）：已全 NULL 的行不再 UPDATE，不白推 `rps` 域 revision。日志里的计数是**行数（rowcount）**，不是单元格数 |
| 前端缺失显示 | `Research.tsx` 第 142-145 行读取 `coverage.data_status`，四类告警均触发横幅（第 302-306 行），**不展示有效研究结果** |

**本轮处置（2026-11-10）**：已完成 `upsert_many` → `upsert_many_fill` 切换、失效单元格显式清空、清理前的三道安全前提与 `IS NOT NULL` 过滤。
回归测试：`tests/test_scan_rps.py` **22 passed**（写层 fill 六场景 + 业务层清理/回填/回滚/历史不改写 + 完整性拒绝/规模拒绝/NULL 幂等/局部失败整日回滚），全量 **960 passed, 3 skipped**。

## G6. 盘后采集观察 1 个交易日

**关键事实（已核实）**：调度器在一个交易日内有多个 cron 触发点，且 `collect_log` 对每个任务记录状态。**实际字段名为 `task`（不是 `job_type`）**，状态取值为 `ok / partial / failed / skipped / empty`。**同日多条 `collect_log` 是正常的**（不同任务 + 重试），不能一概判为重复。

| 检查 | 方法 | 通过标准 |
| --- | --- | --- |
| 无重复成功 | `SELECT task, COUNT(*) FROM collect_log WHERE trade_date=今日 AND status='ok' GROUP BY task HAVING COUNT(*) > 1` | 返回 0 行（同一 `task` 同日不出现多条 `ok`；`partial`/`failed`/`skipped`/`empty` 允许多条） |
| 无锁冲突 | 日志无「采集进行中，跳过」连续出现 | ≤ 1 次/日 |
| 无内存耗尽 | `systemctl show fupan -p MemoryCurrent,MemoryPeak`（生产实测，不用开发估值） | MemoryPeak ≤ 3.2 GB，无 OOMKill |
| 数据落地 | 当日行情/板块/RPS 行数 > 0 | 与上一交易日同量级 |
| 维护窗口避让 | 变更操作不得落在任何定时任务触发时段（见下）；且必须临场核查当时无写入者 | 仅在全部门禁确认后执行 |

**资源基线（历史实测，非当前采样，2026-11-10 补录）**：此前生产运行状态实测值为
`MemoryCurrent = 1740931072 B`、`MemoryPeak = 2120224768 B`、主进程 RSS ≈ `1006 MiB`。
这组数值只代表**当时**的运行状态，**不得冒充本轮或发布时的采样**；正式发布前仍必须按本表
重新做一次只读检查（`systemctl show fupan -p MemoryCurrent,MemoryPeak`，并读主进程 RSS）。

**全部定时任务窗口（变更必须全部避开，不只是 23:00 后）**：

| 时刻 | 任务 | 备注 |
| --- | --- | --- |
| 09:15–09:26（每分钟） | 集合竞价采样 | 交易日 |
| 14:50 | B1 盘中预览 | 只读飞书，不写库 |
| 15:05 | 主采集 | 写库 |
| 17:30 | 收盘补采（龙虎榜/机构/题材/两融/北向） | 写库 |
| 19:30 | 补采重试 | 写库 |
| 20:00 | 收盘链路告警 | 只读 + 飞书 |
| 22:00 | 板块成分股预取 | 写库 |
| 22:30 | 成分股重试 | 写库 |
| 22:35 | 终局收尾（ETF 份额等） | 写库 |
| 23:10 | 数据库备份 | 读库 + 写备份文件 |
| 次日 08:30 | 成分股回看补采 | 写库 |
| 03:30 | 会话清理 | 删 `user_session` 过期行 |

**结论**：23:10 备份任务意味着「23:00 后」**不是**安全窗口。

**维护窗口必须临场核查，不得按固定时段推定（2026-11-10 收紧）**：

- 上表是**当前代码里**的调度窗口，不是永久事实。部署前必须现场核对：①当时的定时任务清单（含系统 crontab / systemd timer 与站内调度器）；②当时的数据库写入者（采集任务、备份任务、手工运维、外部脚本、以及仍连着库的开发进程）。
- **不允许仅凭「周末」或「固定时段」判断窗口安全**；非交易日也要确认没有回补任务、备份任务或人工导入在跑。
- 存在任何活动写入者时，不得执行需要独占的动作（整库替换、`VACUUM`、强制 checkpoint、删表/重建）。
- 确认方式：`SELECT * FROM collect_log ORDER BY id DESC LIMIT 50` 看最近写入、查进程列表与 `lsof`/`handle` 确认无连接，再在窗口开始与结束各确认一次。

**不通过**：保留日志，按《05》回滚到上一版代码（数据一般无需回滚）。

## 附录 A：最小代码修改方案

### A-1. `install_data_revision.py` 增加 `--allow-main-db` 与 `--strict`（已实施）

**状态**：已在开发分支实施并通过测试（`tests/test_install_data_revision.py`，15 passed）。未在生产执行。

**改动内容**：
- 新增 `--allow-main-db` 开关，默认拒绝主库；`--status` 只读不受限；
- 新增 `--strict`：要求 **8 个数据域 / 24 条触发器**；**主库路径自动启用严格口径**，不依赖人记得加参数；
- 严格模式在 `install()` **之前**调用 `_require_all_domains()`，缺任何域表直接拒绝且**零写入**（不会留下半装状态）；
- 安装前调用 `db.schema_report()` 校验 Schema，缺表/缺列/缺索引直接拒绝；
- 安装后 `_verify_triggers(strict=)` 逐条核对五要素：**名称、绑定表、AFTER 事件、`data_revision` 插入、`revision = revision + 1`**；
- 非严格模式（本地/隔离库）只核对「现有表 × 3」，并明示「本地/隔离库结果，不代表生产验收」；
- `--status` 用 `mode=ro` 只读打开，且对不存在的路径直接退出，**不创建空库**。

**验收（开发环境已通过）**：
- `--db <tmp> --strict` → 输出 `db_uuid=...` + `触发器严格校验通过：8 个数据域 / 24 条`；
- 重复执行 → db_uuid 不变、`revision` 不清零、业务数据不丢（幂等）；
- 空库（无业务表）→ `Schema 校验未通过`，不装触发器；
- 缺一张域表 + `--strict` → 安装前拒绝，触发器 0 条；
- 同名但事件不对 / 数据域写错 → 校验失败；
- 默认主库路径 → `拒绝修改主库结构`；加 `--allow-main-db` → 放行并自动严格；
- `--status --db <不存在路径>` → 报错退出，不建库；
- 手动删一条触发器 → `触发器核对失败`。

**生产使用**：`install_data_revision.py --db fupan.db --allow-main-db`（必须在 `migrate_db.py --apply` 之后；主库自动严格，预期输出「8 个数据域 / 24 条」）。

## 2. P0.8-02 真实生产库覆盖审计

### 2.1 审计方法（对生产环境的硬约束）

- 使用**只读连接**：`sqlite3.connect("file:/path/fupan.db?mode=ro", uri=True)`，或 `PRAGMA query_only=1`；
- **禁止通过启动候选应用来「只读查看」生产库**：`backend/app/db.py::init_db()` 在启动时会执行 `Base.metadata.create_all()` 与 `ALTER TABLE ... ADD COLUMN`（补 RPS 4 列、manifest 表、修订表），**启动即迁移**。只读审计必须用独立 SQLite 只读连接，不启动应用；
- **禁止**执行：DDL、DML、`PRAGMA wal_checkpoint`、`VACUUM`、`ANALYZE`、`REINDEX`；
- `PRAGMA quick_check` / `integrity_check` 的深度检查**只在一致性备份副本**上跑，避免占用生产 I/O；
- 逐日覆盖必须**按交易日历外连接**，不得只取 `MAX(trade_date)`。

### 2.2 可直接执行的只读 SQL

```sql
-- 1) 各表规模与首末日期
SELECT 'stock_daily', COUNT(*), MIN(trade_date), MAX(trade_date), COUNT(DISTINCT trade_date) FROM stock_daily
UNION ALL SELECT 'sector_daily', COUNT(*), MIN(trade_date), MAX(trade_date), COUNT(DISTINCT trade_date) FROM sector_daily
UNION ALL SELECT 'sector_member', COUNT(*), MIN(trade_date), MAX(trade_date), COUNT(DISTINCT trade_date) FROM sector_member
UNION ALL SELECT 'rps_daily', COUNT(*), MIN(trade_date), MAX(trade_date), COUNT(DISTINCT trade_date) FROM rps_daily;

-- 2) 逐交易日覆盖矩阵（以交易日历为骨架，缺口显式暴露）
SELECT c.trade_date,
       (SELECT COUNT(*) FROM stock_daily  d WHERE d.trade_date = c.trade_date) AS daily_rows,
       (SELECT COUNT(DISTINCT sector_code) FROM sector_daily s WHERE s.trade_date = c.trade_date) AS sectors,
       (SELECT COUNT(*) FROM sector_member m WHERE m.trade_date = c.trade_date) AS member_rows,
       (SELECT COUNT(*) FROM rps_daily    r WHERE r.trade_date = c.trade_date) AS rps_rows
FROM trade_calendar c
WHERE c.trade_date BETWEEN '2026-09-25' AND date('now')
ORDER BY c.trade_date;

-- 3) 2026-07-03 ~ 2026-09-24 是否已有历史成分股
SELECT trade_date, COUNT(*) AS rows, COUNT(DISTINCT sector_code) AS boards
FROM sector_member WHERE trade_date BETWEEN '2026-07-03' AND '2026-09-24'
GROUP BY trade_date ORDER BY trade_date;

-- 4) manifest / 修订表是否已存在
SELECT name, type FROM sqlite_master
WHERE name IN ('sector_member_backfill','sector_member_backfill_run','data_revision','data_revision_meta');

-- 5) 最新成功采集时间与最近失败/重试（表名 collect_log，只读）
SELECT task, MAX(created_at) AS last_ok
FROM collect_log WHERE status IN ('ok','partial') GROUP BY task ORDER BY last_ok DESC;

SELECT created_at, trade_date, task, status, rows, substr(message, 1, 120) AS msg
FROM collect_log WHERE status IN ('failed','skipped','empty')
ORDER BY created_at DESC LIMIT 50;
```

## 3. P0.8-03 RPS 7,277 行差异解释

### 3.1 三个口径的数字（先对齐定义）

| 口径 | 数字 | 含义 |
| --- | ---: | --- |
| B0 回补脚本自报写入 | **1,269,453** | `b0_rps_backfill_250.json` 的 `total_rows`，250 个交易日（2025-09-22 ~ 2026-10-09） |
| B0 目标库该区间的实际行数 | **1,269,496** | = 1,269,453 + **43** 行回补前就存在、回补脚本不产出的行 |
| B0 目标库全表 | **1,274,587** | 251 天 = 1,269,496 + 2026-10-21 的 5,091 行 |
| P0.7 导入源（`rps60 IS NOT NULL`） | **1,257,023** | 导入脚本实际读取的行 |
| P0.7 目标库导入前 | **10,206** | 10-09 的 5,115 + 10-21 的 5,091 |
| P0.7 目标库导入后 | **1,262,176** | 新增 1,251,970 + 原有 10,206 |
| 差额 | **7,277** | 1,269,453 − 1,262,176 |

### 3.2 完整对账链（每一步都可独立复算）

```
B0 写入                          1,269,453
  − 写入行中 rps60/ret60 为空      −12,430   ← 导入脚本按 rps60 IS NOT NULL 过滤
  = 导入源                         1,257,023
  + 目标库保留、来源不提供的行      +5,153   ← 10-09 的 62 行 + 10-21 的 5,091 行
  = 导入后目标库                   1,262,176

1,269,453 − 1,262,176 = 7,277 = 12,430 − 5,153
```

三项交叉验证：

1. `1,251,970`（新增）`+ 5,053`（已存在并补值）`= 1,257,023` ✅ 与导入源完全一致；
2. 逐日 `imported_new_keys` 求和 `= 1,251,970`，逐日 `target_rows_after` 求和 `= 1,262,176` ✅（见附录 B 的 CSV）；
3. 目标库 10-09 的 5,115 行中，5,053 行在来源侧 `rps60` 非空、62 行为空 ✅ 与 `overlap=5,053 / target-only=62` 一致。

### 3.3 12,430 行的构成

| 分类 | 行数 | 说明 |
| --- | ---: | --- |
| `rps60/ret60` 为空、但 `ret20/rps20` 有值 | **10,747** | 上市不足 60 个交易日的新股（如 10-09 的 155 只，历史中位数 35 根） |
| 四个新字段全为空 | **1,683** | 上市不足 20 个交易日 |
| 合计（250 日区间内，剔除 43 行 legacy） | **12,430** | 与 §3.2 一致 |

### 3.4 5,153 行的构成（目标独有）

| 分类 | 行数 | 证据 |
| --- | ---: | --- |
| 2026-10-09 目标有、来源 `rps60` 为空 | **62** | 其中 **43** 行当天**没有日线**（停牌），是旧版扫描写入的 legacy 行（43/43 行 `ret50=rps50=NULL`、`ret120` 有值，其中 2 行 `ret250` 也为空）；另 **19** 行当天有日线但 60 日窗口覆盖仅 65.0%~86.7% < 90%，新字段按口径应为 `NULL` |
| 2026-10-21 旧版扫描 | **5,091** | `ret50/rps50` 全为 `NULL`，是 50 日窗口上线前的混版本数据；日期晚于底层行情末日（见 §3.6） |

43 行 legacy 的意义：**当前代码不会产出它们**——`scan_rps.flush()` 要求「最后一根 K 线等于目标日」。它们只存在于旧版扫描结果中，不应被当作可信历史。

### 3.6 时点一致性（重要）

- `rps_daily` 最新 **2026-10-21**，但 `stock_daily` 最新 **2026-10-09**。10-21 的 5,091 行 RPS **没有可复现的底层行情**，属于孤儿行。`collect_log` 显示 `kline` 最后一次成功是 10-10、无 10-21 的成功采集记录，进一步说明这批行不是按当前链路产生的。
- 用 10-21 请求研究接口时：`trend` 的候选来自 `rps60 IS NOT NULL` → 0 条；`low-start` 的 250 日窗口内只有 **242** 个有行情的交易日（< 250）→ 全部跳过。**不会**用 10-09 的 K 线冒充 10-21 的结果，但接口返回的是空列表，没有说明原因（见 §7.2 G-1/G-2）。
- 反向情况（有行情、无 RPS，如 09-28）：`trend` 同样返回空列表；`low-start` 会返回行，但 `rps20=NULL` 且 `missing=[]`，页面看不出「RPS 缺失」。
- 窗口完整性：回补 250 天**跳过 0 天**（无一天被当日覆盖率闸拦下）；`rps60` 分母区间为 **4,962 ~ 5,093** 只（每个交易日 60 日窗口覆盖 ≥90% 才有值），250 日窗口首日分母 4,917。不存在「窗口不足却写值」的日期。
- **结论**：不存在「用晚于底层行情的 RPS 生成正常结果」的路径；但存在「缺失被静默忽略」的表达缺陷，属数据门禁问题，不是计算错误。

### 3.7 结论与修复建议（本轮不改生产）

7,277 行差异**已完全解释**，无数据丢失、无冲突、无未来函数。但导入过滤条件 `rps60 IS NOT NULL` **过窄**：

- 影响：**10,747** 条 `(trade_date, code)` 的 `ret20/rps20` 没有进目标库，其中 **10,736** 条目标库连行都没有（另 11 条在 10-09 已存在，但 `ret20` 仍为 `NULL`）；
- 建议（需单独批准后执行）：导入门槛改为「**四个新字段任一非空**」，并对四个字段**逐列** `COALESCE`；

## 4. P0.8-04 Schema 差异（完整矩阵）

对比基线：本机 `fupan.db`（生产等价基线） vs 研究候选 `b1_research.db`（迁移后形态）。

| 对象 | 生产当前 | 候选 | 迁移方式 | 风险 | 回滚 |
| --- | --- | --- | --- | --- | --- |
| `rps_daily.ret20/ret60/rps20/rps60` | 不存在 | 存在（4 列，均为可空 `FLOAT`） | `scripts/migrate_rps_columns.py --apply`（仅 `ADD COLUMN`） | 低：不改旧列、不重建表 | SQLite ≥3.35 `DROP COLUMN`；否则一致性备份恢复 |

| `sector_member_backfill_run` | 不存在 | 21 行 | 同上 | 低 | `DROP TABLE` |
| `data_revision` | 不存在 | 8 行（8 个域） | `scripts/install_data_revision.py` | 中：触发器写放大 | 先删触发器再删表 |
| `data_revision_meta` | 不存在 | 1 行（`db_uuid`） | 同上 | 中：身份变化会导致缓存全失效 | 同上 |
| 8 域 × 3 = 24 个触发器 | 不存在 | 存在 | 同上 | 中：批量导入期间必须先不装 | 同上 |
| 其他表 / 索引 | — | — | **无差异**（`only_in_prod` 为空、无索引差异） | 无 | — |

**执行顺序（不可调换）**

1. 一致性备份（在线备份 API）→ `quick_check`；
2. Schema 迁移（4 列 + 2 表）；
3. 历史数据导入（**此时还没有触发器**）；
4. 安装修订表与 24 个触发器；
5. 启动候选应用，验证 `data_revision.status() == ready` 与缓存行为；
6. 失败则停应用 → 恢复备份 → 重装旧版。

理由：先导入再装触发器，避免数百万行逐行写修订版本；但要求导入阶段应用的读操作**不依赖**修订水位（当前实现是 fail-closed：未装即不缓存）。

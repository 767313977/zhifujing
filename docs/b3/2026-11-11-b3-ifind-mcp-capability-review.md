| 问题 | 结论 |

## 1. 代码审查：三个行情入口

`backend/app/sources/ifind.py`

| 入口 | 模式 | 批量 | 历史日 | 结论 |
| --- | --- | --- | --- | --- |
| `stock_quotes()` → `stock_highfreq_quotes` | `real_time` / `highfreq`（分钟） | **每批 10 只**（`ifind_max_symbols`） | ❌ 只给当日/分钟 | 不能用于历史日 |
| `stock_history()` → `get_stock_performance` | 自然语言，**单票** | ❌ | ✅ | 5,108 只/日 = 5,108 次，**不可行** |
| `search_stocks()` / `search_stocks_full()` | 自然语言**选股器** | ✅ 全市场（分段） | ❓ **未证实** | 唯一候选 |

`search_stocks_full` 的既有事实（代码与注释）：

- 表格最多 **100 行**，静默截断；
- CSV 最多 **1000 行**，超限不退化成「更多」；
- **CSV 下载不占 tools/call 配额**（走 `o.thsi.cn` 静态域名），只算带宽不算次数；
- 因此必须**按代码段分段**，并用 `matched > returned` 判断是否取全；
- 生产已用这套分段法取全市场（注释：全 A 5,569 只）。

也就是说：**「分段 + CSV 取全市场」这个机制是成熟的**；缺的只是「选股器能否按历史交易日
返回行情字段」这一条证据。

共 **14 段，每段 < 1000 行**（最大 927），天然满足 CSV 上限。

- 保守方案：**14 次/日**（每段一次查询，CSV 不计次）；
- 若选股器的查询支持代码区间合并，可压到 **6 次/日**（927 / 932 / 942 / 993 / 852 / 462
  六个 ≤1000 的桶），但**需试验确认区间语法**。

| 场景 | 预热 20 日 | 现有 3,268 能撑 |
| --- | ---: | --- |
| 14 次/日 | 280 | 预热后余 2,988 ≈ **213 个交易日** |
| 6 次/日 | 120 | 预热后余 3,148 ≈ **524 个交易日** |

注意：这 3,268 是**账号级共享额度**，生产采集也在用。建议给研究设上限
（例如 ≤40% ≈ 1,300 次），并预留生产余量。

## 3. 字段、行数、截断与许可

| 项 | 现状 |
| --- | --- |
| 单次返回行数 | 表格 100 / CSV 1000；`matched` 是匹配总数 |
| 截断识别 | 只能用 `matched > len(rows)`，**不能信回答里的文案**（固定模板写 1000，实际 100/1000） |
| 字段 | 由自然语言查询决定；OHLC/涨跌幅/成交额能否同时返回**未证实** |
| 字段缺失 | 选股器可能对不适用字段返回空串；需试验看列名与空值率 |
| 调用计数 | 只计 `tools/call`；CSV 下载不计次；限速 4 req/s |
| 数据许可 | MCP 个人基础版是否允许**本地留存 + 因子计算 + 回测**，仓库无证据 → 需你向供应商确认 |
| 与生产共用 | 同一 token/账号，**必然共用** 3,268 次配额 |

## 5. 建议

1. **不要把 MCP 当唯一主源**：核心能力（历史日多股票）未证实，且与生产共用 3,268 次额度。
2. **先用 3 次请求做判定**：
   - 若选股器支持历史日行情 → MCP 可承担每日增量（6~14 次/日），Tushare 可暂缓；
   - 若不支持 → MCP 只能做交叉校验，主源回到 Tushare 120 分（40 日回补 40 次）。
3. **保留 iFinD MCP 现有功能不动**：认证、配额、生产任务一律不改。
4. 无论走哪条，`pct_source` 必须分区，官方值与历史腾讯推算值不得混用。

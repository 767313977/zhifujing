## 2. 从 NO-GO 转 GO 的必要条件

1. **运维 A**：回传 `free -m`、`nproc`、`systemctl show/cat fupan`、`ps`，以及一次
   真实盘后采集期的 RSS 峰值、Swap、cgroup 上限、nginx 超时、磁盘可用空间；
2. **运维 B**：在生产库的**一致性副本**上跑 `scripts/schema_inventory.py` 与逐日
   覆盖 SQL，回传脱敏结果；
3. **运维 C**：提供生产备份副本（受控环境、不入库、不外传），研发按
   `P1.0-B §5` 重演 8 步并出具对账；
4. **研发**：若 C 与 B 有差异，按差异补迁移分支并补测试（仍需本地 commit 审批）；
5. **项目负责人**：在 1~4 完成后分别批准迁移、导入、部署。

## 3. 明确不允许的动作（本轮及授权前）

- push / 合并 / 部署；
- 生产库迁移、生产历史数据导入、触发器安装；
- 新增日期的全板块补采、修改生产调度、切换正式 Track；
- 用本机 `fupan.db` 或发布等价副本替换生产库；
- 用 `fupan.db` 文件时间作为生产状态证明。

## 4. 回滚方案（已演练）

| 层 | 动作 | 结果 |
| --- | --- | --- |
| 应用 | 停新版本，启动上一版本（`>= c8b5a0d`） | 只验证 Schema，不改库 |
| 数据库 | 恢复迁移前一致性备份（在线备份 API） | 旧结构 + 旧数据 + `quick_check=ok` |
| 组合 | 旧库 + 新应用 | 启动**失败并提示迁移**，不会偷偷改库 |
| 反向 | 新库 + 旧应用（< `915a75a`） | ⚠️ 会触发旧版的 `init_db()`；回退时必须连库一起回退，或先设 `FUPAN_SCHEMA_MODE=verify`（仅新版支持） |

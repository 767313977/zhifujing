## 一、Schema 指纹口径（TRA A）

### 1.1 `47 表 / 423 列 / 21 索引` 来自哪里

来自 **SQLAlchemy 模型元数据**，不是生产库、也不是 SQLite 实际对象统计：

```
scripts/release_manifest.py::schema_fingerprint()
  → 在临时空库上执行 db.migrate_schema()（= Base.metadata.create_all + 补列 + 补索引）
  → sqlalchemy.inspect() 逐表读列（name / type / nullable / default）
  → 读「模型里显式声明的索引」
  → 按 (表名, 列名, 类型, 可空, 默认值) 与 (表, 索引名, 唯一, 列) 排序后 sha256
```

本机复算：

| 统计 | 值 | 口径 |
| --- | ---: | --- |
| `len(Base.metadata.sorted_tables)` | **47** | 模型表 |
| `sum(len(t.columns))` | **423** | 模型列 |
| `sum(len(t.indexes))` | **21** | **模型显式索引** |
| 指纹 | `8dc4309a…` | 以上三项 + 列定义 |

### 1.2 与 P1.0 的 `52 表 / 67 索引 / 24 触发器` 的关系

P1.0 的数字来自 **实际数据库**（`scripts/schema_inventory.py` 对发布等价副本），两者不是同一把尺子：

| 对象 | 模型/指纹（47/423/21） | 实际库（52/67/24） |
| --- | --- | --- |
| 模型表 | ✅ 47 | ✅ 47 |
| 历史遗留表（模型已不再声明、但库中保留） | ❌ | ✅ 1 |
| `sector_member_backfill` / `_run` | ❌（不在 `Base.metadata`） | ✅ 2 |
| `data_revision` / `data_revision_meta` | ❌ | ✅ 2 |
| SQLite 隐式索引（PK / UNIQUE 的 `sqlite_autoindex_*`） | ❌ | ✅ 计入 67 |
| 触发器（8 域 × 3） | ❌ | ✅ 24 |
| 视图 | ❌ | ✅ 0（本库没有） |

所以：

- **指纹**回答的是「这版应用期望什么 Schema」，用于给发布候选打版本号；
- **inventory** 回答的是「这个库实际有什么」，用于生产审计与迁移后验收；
- 二者数字不同是**设计如此**，不需要、也不允许为了对齐而改库。

### 1.3 指纹覆盖 / 不覆盖

| 覆盖 | 不覆盖 |
| --- | --- |
| 模型表的存在 | 触发器及其 SQL |
| 列名、类型、可空、默认值 | 隐式索引（PK/UNIQUE 自动索引） |
| 模型显式索引（含唯一性、列顺序） | manifest / 修订表、视图 |
| —— | 数据内容、`db_uuid`、`data_revision` 版本 |

### 1.4 生产迁移之后用什么工具验证

分三层，缺一不可：

1. **应用期望层**：`python scripts/migrate_db.py --db <生产副本> --status`
   → 必须 `兼容=True`（缺表 / 缺列 / 缺索引都会列出来）。
2. **实际对象层**：`python scripts/schema_inventory.py --db <生产副本> --json after.json`
   以及对候选基线 `--compare`：核对表 / 列（类型、非空、默认）/ 索引 / 触发器 / 视图。
3. **修订层**：`python scripts/install_data_revision.py --db <生产副本> --status`
   → 8 个域、24 个触发器、`db_uuid` 存在、`cache.state=ready`。

> 禁止通过启动候选应用来检查生产 Schema —— 启动会走 `ensure_schema()`（虽然默认
> verify 不写库，但这不是审计手段）；审计必须在**副本**上用上述只读工具完成。

### 1.5 指纹不一致时如何阻断

| 场景 | 判定 | 动作 |
| --- | --- | --- |
| `migrate_db --status` 不兼容（缺模型对象） | **阻断** | 说明迁移未完成或失败，禁止启动 |
| `schema_inventory` 出现「仅生产有、候选没有」的**列或表**且未登记 | **阻断** | 人工评审；不得删列/删表 |
| 同名同列但**类型 / 非空 / 默认值**不同 | **阻断** | 不得自动 ALTER；出方案后单独批准 |
| 触发器不足 24 或名称不符 | **阻断** | 重装修订水位 |
| 指纹与 RC Manifest 不同 | **阻断** | 说明应用源码不是冻结版本（构建来源错误） |
| 仅多出已登记的 manifest / 修订表 / 遗留表 / 隐式索引 | 允许 | 记入报告，不算差异 |

**注意**：指纹是「应用版本」的标识，生产库与它不同不一定是错；真正的门禁是上面第 1、2、3 层。
报告中的数字差异不得通过删对象来「对齐」。

## 二、发布包白名单与敏感信息排查（TRA B）

### 2.1 打包方式

使用仓库自带的 `scripts/pack_deploy.py`（白名单）：

```
INCLUDE = backend/app, backend/requirements.txt, frontend/dist, scripts, deploy
```

它同时做了三件事：只收白名单；拒绝「已跟踪但有未提交改动」；跳过「未跟踪且未被忽略」的文件
（防止把别人正在写的源码打进包）。**没有**对整个工作目录执行压缩。

```bash
python scripts/verify_release_package.py \
    --archive dist-deploy/fupan-fe2005f.tar.gz \
```

> 两个可复现性注意点（不影响本次结论）：
> 1. 工作区是 CRLF、Git blob 是 LF，直接比 `sha256(git show)` 会全部不一致；
>    必须用 `git hash-object --path=` 让 Git 应用同一套换行过滤。
> 2. `frontend_dist.digest` 的排序沿用了 Windows `PurePath` 的不区分大小写顺序；
>    跨平台复算时要按清单记录的顺序，或后续把排序改成显式 `casefold`（属改进项，未改）。
